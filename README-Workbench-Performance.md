# Lab / Glass and shared loading performance

Version: 20261027-performance-1

The shared RPC client incorrectly announced successful read requests whose read flags were inside an any-of permission rule as writes. The recurring Parts counts reader could therefore trigger another workflow refresh repeatedly on every open application tab. Read-only rule recognition now handles nested any-of rules. The two affected count rules are explicitly marked read-only in the server and client catalogs. Successful writes still announce immediately; failed writes and permission denials do not.

Lab / Glass technician selection now reads pending rows, receipt/device metadata, Parts plans, services and pending legacy returns through one authorized get_lab_workbench_v1 call. IMEI scanning resolves primary/secondary identity, current technician and the matching pending phone in that same request, and returns just the matching line. The original Office, active-staff, page View/Search and TV checks remain in force. Secondary IMEI shows the duplicate notice. The new read does not expose private Parts prices and applies the existing supplier-name permission.

Concurrent identical workbench and board reads share their in-flight promise without retaining completed results. A later card selection, scan or edit wins over older responses. Clicking the selected card again sends no duplicate read. Unchanged background payloads retain existing row nodes and drafts. The old per-technician plan-reader limit of 250 does not apply to the combined endpoint. Parts ordering, returns, services, completion and their revision checks use the existing write routines.

Shared notification count reads run in parallel. Unchanged counts do not trigger unnecessary downstream refresh events, while confirmed writes, database signals, account changes and changed counts still do. The existing notification polling intervals are retained. Employee subscribers are called when their roster changes or an explicit employee update is announced, rather than on every identical read. Employee polling no longer follows every notification poll. Lab badges retain their five-second fallback board read.

Exact 15-digit IMEI submissions on IMEI Search use the native exact journey reader directly, avoiding the extra suggestions lookup. That native reader supports primary and secondary IMEIs. Partial IMEIs, model names, serial/invoice searches and suggestions retain their normal behavior. Fourteen additive indexes support pending steps, jobs, work orders, QC findings/requirements, part requests/returns, services, and device identifiers. No business records or stock quantities are rewritten.

Validation: disposable PostgreSQL with native functions through 209; assigned/unassigned scan, secondary IMEI, moved/missing phones, 250+ phone cards, View versus Search, Office/TV/anonymous guards, replay and earlier version receipts. Browser coverage includes one-read card/scan, rapid selection and scan races, unchanged-refresh drafts, single-flight reads, services, employee refresh, View Only, mobile/dark, Frame, exact IMEI and absence of background count loops. The existing 15-case notification regression suite covers bulk commits, cross-tab updates, remote signals, hidden tabs, failures and sign-out. Local fixtures do not establish live internet or database response times.

Run outputs/Publish-GreenLoop-Performance.ps1. The publisher verifies the preceding database version and selects the required additive SQL before publishing pinned files. Required final SQL result: installed_performance_version = 20261027-performance-1. No Edge Function or JWT setting change is required. Live installation and publication are confirmed by the publisher, not by local tests.

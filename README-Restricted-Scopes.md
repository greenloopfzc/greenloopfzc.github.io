# Restricted Data - supplier, invoice, batch and IMEI-list deletion

Release: 20261030-restricted-scopes-1
Database marker: get_restricted_scopes_version() = 20261030-restricted-scopes-1
Installer result: installed_restricted_scopes_version

Reports > Restricted Data keeps Delete a single IMEI and Reset all IMEIs, and adds Delete by Supplier, Delete by Invoice, Delete by Stock/Batch and Delete multiple IMEIs. Each new scope has a separate Reports capability tick. Supplier/invoice/batch actions require Owner or Super Admin; an authorised Manager can use the IMEI-list action. Entry rights never imply these permissions. Existing Owner/Super Admin accounts with Reports Reset all rights receive the narrower new scope ticks; ordinary staff grants are unchanged. No Edge Function or JWT change is required.

Selections use exact database IDs. Invoices are grouped by complete invoice number AND supplier ID, so the same invoice number for another supplier remains separate. All matching receipts, including receipts without entered phones, are included. Phones are included at every operational stage, including Ready Stock and export boxes. IMEI lists accept either IMEI and deduplicate aliases for the same phone; previews display IMEI 1. No selection is inferred from a partial code. Search choices page on the server, and stale search responses cannot replace a newer selection.

The preview lists exact phone and receipt counts, stages, phone details and planned receipt quantities. It supports paging through the complete preview. Each execution requires a reason, the existing authorised deletion code, exact typed confirmation and a token over the complete current selection. Any change to selected public or private workflow records invalidates the token. No deletion is performed during installation or preview. The supplier option defaults to also archiving the supplier profile from future receipts; it can be unchecked to retain that profile for future stock. Invoices and batches never remove supplier profiles.

Deletion is one transaction. The implementation extends the reviewed deletion planner/executor without changing the legacy entry points. It retains dependency/cross-link checks, exact row matching, archived supplier-return history, box workflow rules and existing stock restoration rules. Shared receipts and boxes retain their unrelated phones. Conflicting supplier/receipt assignments stop the deletion for review instead of removing another supplier's records. Only unused issued parts are restored under the existing rule; physical professional inventory lots and balances remain unchanged.

Active private Parts, replacement-source and Lab service records are archived and removed with their selected phones, including Initial QC direct-Parts links. Permanent audit rows remain. Full private snapshots (including private Parts prices and archived supplier profile data) are held in an RLS-protected private archive linked to Deleted History; raw private prices are not added to the public history payload. Live Damage Report, independent Available Stock manual entries, employees/options, other suppliers and unrelated phones stay separate. Supplier names in choices/search follow the existing confidential-name permission.

Migration 223 adds the protected scope functions/archive, four catalog capabilities and reviewed office wrappers. It preserves all previous version markers. The cumulative PowerShell publisher verifies earlier installations before requesting this SQL, copies SQL only for a missing new marker, and never publishes on a changed marker or failed check. Run the complete clipboard SQL in a NEW Supabase query. The script only installs features; actual deletion is a later reviewed action in Reports.

Validation uses disposable PostgreSQL and browser fixtures only: 23 database groups, 20 browser cases, HTTP/checker failures and publisher rehearsals. Covered cases include Ready Stock, identical invoice numbers across suppliers, empty receipts, IMEI 2 aliases, private workflow cleanup and price privacy, supplier-return archiving, shared boxes, stale tokens, cross-supplier conflicts, bad codes, role/grant denial, unknown dependencies and late-error rollback. Existing 75 verification components and newer QC/Parts markers remain valid. No live records were deleted or modified during testing.
